Architecture

Clients call REST endpoints through Nginx. NestJS validates payloads globally, applies JWT guards where required, writes durable financial state to PostgreSQL, uses Redis for hot account lookups and replay protection, and publishes domain events into RabbitMQ after successful business actions. Notification consumers process those events asynchronously and send email through Brevo, with SMS using a mock provider by default and Termii support available through environment configuration.

REST API

Auth, accounts, transfers, webhooks, NIBSS mock, reconciliation, settlements, metrics, health checks.

PostgreSQL

Users, accounts, transactions, ledger entries, notifications, audit logs, indexed lookup paths.

Redis

Account cache, TTL reads, cache invalidation after transfers, webhook replay keys.

RabbitMQ

Async domain events for registration and transfer notification workflows.

Likely Interview Questions and Answers

Q: Why NestJS for this banking backend?

A: NestJS gives clear module boundaries, dependency injection, guards, pipes, interceptors, Swagger integration, and microservice support. For a regulated fintech backend, that structure helps teams keep auth, transaction logic, notifications, audit, and integration code separated and testable.

Q: How do you protect financial transfers from race conditions?

A: The transfer service runs debit and credit inside a database transaction. It locks both account rows using deterministic ordering so two transfers touching the same pair of accounts do not deadlock randomly. It validates sufficient funds, writes transaction and ledger records, commits atomically, and rolls back on error.

Q: What does deterministic account locking mean?

A: It means accounts are locked in a stable order, for example by account number, regardless of which one is the sender or receiver. If two concurrent transfers touch the same accounts, both code paths request locks in the same order, reducing deadlock risk.

Q: How would interbank transfer work with two different banks?

A: The same local debit still needs a database transaction and ledger entry. The external bank leg should be represented as an outbound payment instruction with a state machine such as PENDING, SENT, CONFIRMED, FAILED, or REVERSED. NIBSS/name enquiry validates destination details, settlement/reconciliation verifies the external outcome, and compensating reversal is used if the debit succeeds but external settlement fails.

Q: Why use RabbitMQ here?

A: Transfers and registration should not wait on email or SMS providers. RabbitMQ decouples the core financial commit from slower side effects. The API commits the transaction, publishes a domain event, and consumers send notifications asynchronously.

Q: Why use Redis?

A: Redis handles fast account lookup caching and webhook replay protection. Account cache reduces repeated PostgreSQL reads, while replay keys prevent the same webhook event ID from being accepted twice within the replay window.

Q: How are webhooks secured?

A: The endpoint verifies an HMAC SHA256 signature, checks that the timestamp is within a freshness window, and stores event IDs in Redis with a TTL so duplicate webhook delivery cannot be processed twice.

Q: What is the purpose of reconciliation?

A: Reconciliation compares expected financial movements with actual ledger records. In this app it checks successful transactions against double-entry ledger rows. In a real bank it also compares internal records with processor, NIBSS, card, or settlement files.

Q: What would you still improve before a regulated production launch?

A: Add a real cloud secrets manager, centralized logs, distributed tracing, deeper e2e tests with isolated containers, formal admin user provisioning, payment provider sandbox integration, full settlement file ingestion, fraud/risk checks, rate limits per customer, and Kubernetes/cloud deployment automation.
